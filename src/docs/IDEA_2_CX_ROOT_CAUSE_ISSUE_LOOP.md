# [Idea 2 종합 보고서] 10배 인재밀도를 위한 CX-to-Dev Root Cause Automated Loop System

## 1. 리서치 배경 & 객관적 근거 (Research & Evidence)

### 1.1 공개 시장 데이터 및 현황
- **CS 데이터와 서비스 개발의 파편화**: SaaS 및 이커머스 기업에서 발생하는 CS 문의의 **약 35~40%**는 서비스 버그, UX 결함, 설명서 부재 등 '서비스 개발/기획 문제'에서 유발됨.
- **소통 병목 지수**: CS 담당자가 고객 불만을 개발팀에 전달하는 과정에서 정보 누락, 단순 전달에 그침으로써 해결까지 평균 **4.2일** 소요.
- **기존 방식의 한계**:
  - CS 챗봇이나 상담사는 당장의 고객 응대(Firefighting)에 급급하여 "왜 이 문제가 반복해서 발생하는가?"를 분석하고 개발 티켓으로 만들 시간이 부족함.

### 1.2 채널톡 리서치 & 대표 인터뷰 연계성
- **채널톡 인터뷰 내용 연계 (02:24–03:14 & 03:58–04:50)**:
  > *"표면적인 사용법보다 '왜 그런 현상이 발생하는가?'처럼 문제의 본질을 탐구하는 태도가 핵심"*
  > *"직원 200명이더라도 한 사람이 10명 이상의 생산성을 낼 수 있는 인재 밀도(Talent Density)를 높이는 것이 경쟁력"*
- **시사점**: CS 담당자 1명이 단순 상담을 넘어 '제품 품질 관리자 및 기술 이슈 분석가' 수준의 10배 인재 생산성을 갖출 수 있도록 지원하는 프레임워크.

## 2. 문제 정의 (Problem Statement)

> **"수천 건의 CS 문의가 인입되지만, '왜 발생했는가?'에 대한 본질적 원인 파악이 되지 않아 동일한 버그와 UX 불편이 매달 반복되어 리소스가 낭비된다."**

1. **단발성 파이어파이팅**: 상담사는 고객 불만을 끈기 있게 청취하지만, 개발팀이 이해할 수 있는 재현 절차(Reproduction Steps)나 에러 로그 형태로 변환하지 못함.
2. **조직 간 격차(Silo)**: CS팀(채널톡)과 개발팀(GitHub/Jira) 간 데이터 전달 체계 부재.
3. **인재 생산성 한계**: 문제 원인 분석을 위해 개발자/PM/CS리드가 모여 주간 회의를 거쳐야만 이슈화가 가능함.

## 3. 솔루션 아키텍처 & 스코프 (3~4주 공수 엔터프라이즈 설계)

본 솔루션은 **CS 대화 텍스트 분석 ➔ Root Cause 추론 ➔ 개발/제품 개선 아티팩트 자동 생성 ➔ 루프백**을 수행하는 엔터프라이즈 루프 시스템입니다.

```text
[채널톡 CS 대화 데이터]
       │
       ▼
┌───────────────────────────────────────────────────────────┐
│ Module 1: Root Cause & Defect Taxonomy Pipeline           │
│  - 단순 문의 vs 기술적 버그 vs UX 파손 vs 안내부족 자동 판별│
└──────────────────────────┬────────────────────────────────┘
                           │
                           ▼
┌───────────────────────────────────────────────────────────┐
│ Module 2: Tech Analysis & Bug Reproduction Agent         │
│  - 고객 진술 기반 재현 단계(Steps to Reproduce) 및       │
│    예상 원인 코드/API 추론                                │
└──────────────────────────┬────────────────────────────────┘
                           │
       ┌───────────────────┴───────────────────┐
       ▼                                       ▼
┌───────────────────────────────┐   ┌───────────────────────────────┐
│ Module 3: SDLC Ticket & PR    │   │ Module 4: Knowledge-base      │
│           Generator (MCP)     │   │           Auto-Updater        │
│  - Jira/GitHub Issue 자동 생성 │   │  - 채널톡 FAQ / 가이드 아티클 │
│  - PR (Pull Request) 초안 작성│   │    개선안 자동 작성            │
└───────────────────────────────┘   └───────────────────────────────┘
```

### 🛠️ 4대 핵심 모듈 및 3~4주 공수 명세
1. **Module 1: Root Cause & Defect Taxonomy Pipeline**
   - 대화 내역에서 표면적 불만 뒤에 숨은 본질적 원인을 NLP 카테고라이징(API 타임아웃, 결제 UI 짤림, 안내문구 오해 등).
2. **Module 2: 기술 분석 및 이슈 재현 에이전트 (Codex Skill)**
   - 비기술자인 CS 담당자를 대신해 "OS/브라우저 환경, 발생 단계, 영향도"를 정형화된 디버깅 리포트로 구성.
3. **Module 3: SDLC (Jira/GitHub) 이슈 & PR 생성 MCP**
   - 개발자가 즉시 조치할 수 있도록 GitHub Issue를 생성하고, 간단한 안내 문구 수정의 경우 문서 PR까지 자동 발급.
4. **Module 4: 채널톡 지식베이스(FAQ) 자동 업데이트 에이전트**
   - 반복 문의 발생 시 채널톡 아티클/FAQ 수정안을 작성하여 CS 담당자가 클릭 한 번으로 반영 가능하게 함.

---

## 4. 검증 방안 (Verification Plan)

1. **정량적 검증 (Root Cause Extraction Accuracy)**:
   - 500건의 실제 CS 상담 록 데이터셋(버그, UX, 단순 문의 혼재)을 대상으로 본질적 원인 분류 정확도 측정 (Target: 90% 이상).
2. **정성적 검증 (Developer Review)**:
   - 생성된 GitHub Issue 및 PR의 품질(재현 가능성, 설명 명확성)을 현직 개발자 관점에서 검증.

## 5. 해커톤 5개 질문 사전 답변 준비

1. **무엇을, 누가, 어떤 상황에서 쓰나요?**: CS/CX 팀과 개발/기획팀이 채널톡으로 인입된 고객 문의의 근본 원인을 파악하고 개발 이슈로 즉시 연동할 때 사용.
2. **왜 이 문제를 선택했나요?**: 채널톡 인터뷰의 핵심 메시지인 "문제의 본질 탐구"와 "10배 인재밀도"를 가장 극명하게 보여줄 수 있는 과제이기 때문.
3. **플러그인은 어떻게 작동하나요?**: 채널톡 챗 텍스트 수집 -> Codex 기술 분석 에이전트 실행 -> Jira/GitHub/채널톡 FAQ 자동 업데이트.
4. **AI를 어떻게 활용했나요?**: 비구조화된 대화 텍스트에서 기술적 버그 요소를 추론하고, 개발자용 이슈 템플릿 및 코드 PR 초안을 자동 생성하는 데 LLM 활용.
5. **어떻게 검증했나요?**: CS 로그 데이터셋 500건 분류 정밀도 테스트 및 개발자용 티켓 완성도 평가.

## 6. 보완: 실현성 · 차별화 · 리스크 (Review Addendum)

### 6.1 이 아이디어의 전략적 우위 (Why this wins)

3개 후보 중 **Codex 플러그인과 본질적으로 가장 잘 맞는 아이디어**임을 전면에 내세울 것.

- Codex의 핵심 역량은 "텍스트 → 코드/이슈 아티팩트 생성 + 개발 툴 연동". 본 솔루션은 정확히 그 경로(CS 텍스트 in → GitHub Issue/PR out)라 **데모로 실제 작동을 보여주기 쉬움**.
- Idea 1·3은 실시간 행동 훅/CRM 양방향 동기화 등 외부 의존이 커 4주·데모 실현성이 낮은 반면, 본 건은 입력(대화 텍스트)과 출력(이슈/PR)이 모두 손안에 있음.

### 6.2 ⚠️ 데이터 출처 정직성 (검토 필요)

- "CS 문의의 35~40%가 개발/기획 문제", "해결까지 평균 4.2일"은 **출처 미상**. 현재 단정형 서술은 위험.
- 조치: (a) 실제 출처를 찾아 인용하거나, (b) "내부 가정치" 또는 "본 팀 관찰 기반 추정"으로 재라벨링. 검증 불가 수치를 사실처럼 쓰지 말 것.

### 6.3 해커톤 데모 MVP vs 엔터프라이즈 비전 (스코프 분리)

| 구분 | 범위 | 데모 방식 |
| :--- | :--- | :--- |
| **MVP (실제 구현·시연)** | 샘플 CS 대화 → ①결함 분류(버그/UX/안내부족/단순문의) ②재현 단계 정형화 ③GitHub Issue 초안 생성 | Codex Skill + GitHub MCP, 실제 테스트 리포지토리에 이슈 생성 시연 |
| **확장 (로드맵)** | Module 4 FAQ 자동 PR, Jira 연동, 실시간 파이프라인 | 아키텍처로 제시 |

> Module 2의 "예상 원인 코드/API 추론"은 과장 위험 — 실제 리포지토리 소스가 없으면 추론 불가. 데모는 **재현 단계 + 결함 분류 품질**에 집중하고, 코드 추론은 "리포지토리 컨텍스트가 주어질 때"로 조건부 서술.

### 6.4 채널톡 실제 연동 표면 (Integration Surface)

- **입력**: 채널톡 Open API `userChats`/`messages`, Webhook(`message` 이벤트)로 대화 수집.
- **출력**: GitHub/Jira MCP로 이슈·PR 생성. 채널톡 Manager API로 해당 대화에 "이슈화 완료" 코멘트 회신(루프백 가시화).

### 6.5 기존 채널톡 AI(ALF)와의 차별화

채널톡 AI는 *고객 응대*가 목적. 본 솔루션은 *개발 조직으로의 이관(handoff)* 이 목적 — 응대가 끝난 대화를 **개발자가 즉시 착수 가능한 재현 리포트**로 바꾸는 후공정 계층. 겹치지 않고 보완적임을 명시.

### 6.6 개선된 검증안 (순환논리 제거)

- 자기생성 500건 대신, **공개 CS/버그 리포트 코퍼스** 또는 익명화 실로그 사용.
- 분류 정확도: 라벨러(사람)와 실행자 분리, 혼동행렬 + macro-F1 보고 (단일 "90%" 목표치보다 클래스별 성능 공개가 설득력 큼).
- 티켓 품질: 현직 개발자 3명 블라인드 평가 — "추가 질문 없이 착수 가능한가"를 Yes/No로 집계.

### 6.7 리스크

- **오분류로 인한 잘못된 이슈 양산** → 신뢰도(confidence) 임계값 미만은 사람 검토 큐로.
- 코드/API 추론의 환각(hallucination) → "추정"임을 이슈 본문에 라벨링, 단정 금지.
