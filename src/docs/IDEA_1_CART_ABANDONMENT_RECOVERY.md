# [Idea 1 종합 보고서] 이커머스 장바구니/결제 이탈 자동 회복 & VOE 본질 분석 AI 수트

## 1. 리서치 배경 & 객관적 근거 (Research & Evidence)

### 1.1 공개 시장 데이터 및 현황
- **장바구니 이탈률(Cart Abandonment Rate)**: Baymard Institute 조사 결과, 이커머스 평균 장바구니 이탈률은 **69.99% (약 70%)**에 달함.
- **결제 단계 이탈 원인 분석**:
  1. 예상치 못한 추가 비용 (배송비, 수수료 등) : 48%
  2. 회원가입 강제 : 24%
  3. 결제 프로세스 복잡/오류 : 18%
  4. 상품 상세 정보 부족 / 고객문의 미해결 : 16%
- **기존 방식의 한계**:
  - 기존 팝업 솔루션(Tasmanian, Drip 등)은 단순 할인 쿠폰 팝업만 노출함.
  - "고객이 왜 이탈하려 하는지" 대화나 맥락을 수집하지 못해 결제 에러나 UX 문제로 이탈하는 고객을 구출하지 못함.

### 1.2 채널톡 리서치 & 대표 인터뷰 연계성
- **채널톡 인터뷰 내용 연계 (03:14–03:58)**:
  > *"AI를 활용해 장바구니 이탈 고객에게 인터뷰하거나 구매를 유도하는 등, 단순 상담을 넘어 이커머스 문제를 해결하는 AI 에이전트를 개발하고 있습니다."*
- **시사점**: 채널톡 공식 인터뷰에서 직접 제시한 최우선 과제이며, 채널톡 플랫폼 위에서 동작할 때 비즈니스 임팩트가 가장 큰 영역.

---

## 2. 문제 정의 (Problem Statement)

> **"이커머스 기업은 매달 장바구니 이탈로 매출의 70%를 잃고 있지만, 단순 할인 쿠폰 외에는 이탈 원인을 파악하거나 1:1로 이탈을 회복할 수단이 없다."**

1. **상담/구매 전환 파편화**: 고객이 결제 직전 의문점(배송일, 사양 등)이 생겨도 CS 챗봇이 정형적인 답변만 제공하여 이탈함.
2. **이탈 원인 파악 불가능 (Blackbox)**: 왜 1,000명의 고객이 결제를 포기했는지 원인을 집계하고 분석할 데이터 수집 체계 부재.
3. **인력 부재**: CS 담당자가 이탈 직전 고객에게 일일이 1:1 대화를 걸어 설득하고 이탈 원인을 인터뷰할 물리적 시간이 부족함.

---

## 3. 솔루션 아키텍처 & 스코프 (3~4주 공수 엔터프라이즈 설계)

본 솔루션은 **Codex Plugin + MCP Server + Multi-Agent Workflow**를 결합한 종합 이탈 회복 수트입니다.

```text
[고객 웹/앱 행동 데이터] ──► [Module 1: Real-time Friction Detector (MCP)]
                                         │
                                         ▼
                               [Module 2: Autonomous Recovery Agent]
                                (1:1 실시간 인터뷰 & 맞춤 혜택/해결책)
                                         │
                   ┌─────────────────────┴─────────────────────┐
                   ▼                                           ▼
[Module 3: Root Cause Insight Reporter]       [Module 4: Business Saved ROI Simulator]
 (PG 오류/UX 결함/설명부족 분류 -> Jira 연동)   (회복 매출 추정 및 LTV 예측 리포트)
```

### 🛠️ 4대 핵심 모듈 및 3~4주 공수 명세
1. **Module 1: 실시간 마찰 요소 감지 훅 (Friction Detector MCP)**
   - 장바구니 체류시간 초과, 특정 결제 에러 코드 발생, 상품 상세페이지 반복 이탈 등 이벤트 감지.
2. **Module 2: 자율 1:1 이탈 회복 및 대화형 인터뷰 에이전트 (SKILL.md)**
   - 단순 쿠폰 발급이 아닌 고객의 행동 맥락에 맞춘 대화 시작 ("결제 시 카카오페이 오류가 발생하셨나요?", "배송 관련 궁금한 점이 있으신가요?").
   - 이탈 이유 인터뷰 데이터 자동 수집.
3. **Module 3: VOE(Voice of Customer) 근본 원인 도출 및 루프백 엔진**
   - 수집된 이탈 대화를 Codex가 분석하여 "PG사 결제 모듈 스크립트 에러(기술적 원인)", "옵션 설명 오해(UX 원인)" 등으로 분류 및 Jira/Slack 자동 티켓 생성.
4. **Module 4: Saved Revenue & ROI 시뮬레이터**
   - 방어한 매출 금액(Saved Sales Volume)과 이탈 회복률을 실시간 수치화하여 경영진 리포트 자동 생성.

---

## 4. 검증 방안 (Verification Plan)

1. **정량적 검증 (Simulated A/B Test)**:
   - 1,000건의 이커머스 이탈 고객 시나리오 데이터셋(결제 실패, 배송비 불만, 상품 스펙 의구심 등) 구축.
   - 플러그인 적용 전/후의 구매 전환 성공률(Conversion Recovery Rate) 및 정확한 원인 분류율 측정.
2. **정성적 검증 (Root Cause Accuracy)**:
   - 도출된 Jira 티켓 및 개선안 문서가 실제 개발/마케팅팀이 조치 가능한 수준의 본질적 원인을 담고 있는지 검증.

## 5. 해커톤 5개 질문 사전 답변 준비

1. **무엇을, 누가, 어떤 상황에서 쓰나요?**: 이커머스 마케터 및 CS 담당자가 장바구니/결제 단계에서 이탈하려는 고객을 자율 회복하고 원인을 분석할 때 사용.
2. **왜 이 문제를 선택했나요?**: 이커머스 매출 이탈의 70%가 발생하는 가장 치명적인 구간이며, 채널톡 대표 인터뷰에서도 최우선 강조된 문제이기 때문.
3. **플러그인은 어떻게 작동하나요?**: Codex Plugin이 마찰 이벤트를 감지(MCP) -> 대화형 인터뷰 스킬 발동 -> 원인 추론 및 이슈 티켓팅 자동 수행.
4. **AI를 어떻게 활용했나요?**: 고객 감정/의도 분석, 1:1 동적 회복 메시지 생성, VOE 빅데이터 본질 추론에 Codex LLM 워크플로우 활용.
5. **어떻게 검증했나요?**: 1,000건의 이탈 시나리오 데이터셋으로 이탈 회복률 및 원인 분석 정밀도 테스트 수행.

## 6. 보완: 실현성 · 차별화 · 리스크 (Review Addendum)

### 6.1 ⚠️ 데이터 출처 정직성 (검토 필요)

- **검증된 수치**: 장바구니 이탈률 69.99% → Baymard Institute 통계 맞음 (인용 시 접속연도 명기).
- **재확인 필요 수치**: 본문 이탈 원인 비율(48/24/18/16%)은 Baymard 원문 항목·비율과 미세하게 다름. 발표 전 [Baymard Cart Abandonment Rate Statistics] 원문과 대조하거나, "대표적 원인 예시"로 수위를 낮춰 단정형(48%)을 회피할 것.
- **원칙**: 출처 불명 수치는 "가정(assumption)"으로 명시. 심사에서 수치 하나가 틀리면 문서 전체 신뢰가 무너짐.

### 6.2 해커톤 데모 MVP vs 엔터프라이즈 비전 (스코프 분리)
4개 모듈 전체(실시간 결제 에러코드 훅, PG 연동)는 3~4주로 시연 불가. **실제 제출 데모는 아래로 축소**하고, 나머지는 "확장 로드맵"으로 배치한다.

| 구분 | 범위 | 데모 방식 |
| :--- | :--- | :--- |
| **MVP (실제 구현·시연)** | 이탈 대화 로그(텍스트) 입력 → ①원인 분류 ②맞춤 회복 메시지 생성 ③Saved Revenue 리포트 | Codex Skill + 샘플 로그 파일 |
| **확장 (로드맵)** | Module 1 실시간 마찰 감지 훅, PG 에러코드 연동 | 아키텍처 다이어그램으로만 제시 |

> 핵심: Module 1(실시간 행동 데이터)은 채널톡 **Webhook 이벤트(userChat 생성/메시지 인입)** 로 대체 가능함을 명시. 임의의 결제 에러코드 훅 전제를 버리고, 채널톡이 실제로 주는 이벤트 표면 위에서 설계할 것.

### 6.3 채널톡 실제 연동 표면 (Integration Surface)

- **입력**: 채널톡 Open API `userChats` / `messages` 조회, Webhook(`message` 이벤트)로 이탈 의심 대화 수신.
- **출력**: 채널톡 Manager API로 상담사에게 회복 제안 메시지 초안 전달(자동 발송 아닌 사람 검수형). 원인 티켓은 Jira/Slack MCP.
- 이렇게 "채널톡이 실제 제공하는 API 위에서 동작"함을 밝혀야 재발명이 아닌 플러그인으로 인정됨.

### 6.4 기존 채널톡 AI(ALF)와의 차별화
채널톡은 이미 AI 상담 에이전트를 보유. 본 솔루션의 차별점은 **"응대"가 아니라 "이탈 원인의 구조화 + 개발/마케팅 루프백"** — 즉 개별 답변이 아니라 *VOE를 조치 가능한 이슈로 전환*하는 계층임을 분명히 할 것.

### 6.5 개선된 검증안 (순환논리 제거)

- 정답과 입력을 같은 사람이 만드는 자기생성 데이터셋 지양.
- **held-out 방식**: 실제(또는 공개) CS 로그를 라벨링 담당과 분류 실행을 분리, 사람 라벨 vs 모델 분류 일치율(Cohen's κ) 측정.
- **회복률**은 시뮬레이션으로 단정하지 말고 "메시지 품질에 대한 블라인드 사람 평가(설득력 1~5점)"로 대체해 과장 방지.

### 6.6 리스크

- 이탈 직전 자동 메시지의 **스팸/과공격성** 리스크 → 사람 검수(human-in-the-loop) 기본값.
- 개인정보(결제/구매 데이터) 처리 → 데모는 익명화 샘플만 사용 명시.
